SPECIFICATION COMPARISON

A2UI vs MCP Apps

A2UI describes an interface using trusted components. MCP Apps delivers a custom web app inside a compatible AI host.

Scope: A2UI v0.9 (used by this demo), MCP Apps stable specification 2026-01-26. Checked 8 October 2026. Tradeoffs below are engineering assessments, not guarantees.

A2UI

Controlled, agent-composed UI

Pros

  • Reuse host design-system components.
  • Compose and progressively change layouts with data.
  • Validate structured UI before rendering.

Cons

  • Host must implement catalogs and rendering.
  • Custom widgets require agreed catalog extensions.
  • Agent output still needs semantic validation.
MCP APPS

Custom web app in an AI host

Pros

  • Full web UI flexibility for complex interactions.
  • Standard tool-linked resources and host bridge.
  • App can manage interactions without asking an LLM each time.

Cons

  • Requires a compatible host and iframe lifecycle.
  • CSP, permissions, and host context need integration.
  • Native host styling is not automatic.

They can work together

An MCP App can contain an A2UI renderer: MCP Apps handles delivery and the host bridge; A2UI handles declarative composition inside the view. For this Chợ Tốt example, A2UI suits composing approved listing components; MCP Apps suits packaging a complete listing experience for a compatible AI host.

Primary references: A2UI v0.9 protocol · MCP Apps stable spec.

Where a real backend belongs—and how listing records reach the UI
Production integration: the agent/backend service resolves the intent, calls a listing search service, and passes returned records to the agent and renderer. The tool/service call is an application operation, not an A2UI envelope. The server can create the surface before fetching data; this trace’s summary needs the records before message #2.
User intent→Agent service→Listing backend→Returned records→A2UI + renderer data
These four messages contain no full ad records. Message #4 has only IDs 303 and 302. Our Comparison component looks them up in the preloaded sample inventory. A real integration must deliver records through a bound data model, a shared client cache, or a documented component fetch contract. IDs alone are insufficient when the renderer has no matching records.
On a filter click: the client sends an A2UI action and, because sendDataModel is true, the current model in transport metadata. The server validates the query, calls the listing service again, and emits updates to the existing surface. A2UI does not automatically trigger this search.
On failure: handle loading, no results, stale IDs, and backend errors explicitly. Do not invent listings or send a comparison until its records are available. The example search below is pseudocode, not a verified Chợ Tốt endpoint or parameter contract.
